# 十个任务的论文实验初筛建议

本文依据 2026-10-24 至 25 的 AgentENV v2 单 VM 固定轨迹结果，面向“checkpoint 历史文件层共享 / 增量 DAX”方向提出候选建议。**这是初筛，尚未验证多 VM 物理共享或 DAX 收益，也未实施本文提出的后续实验。** 原始数据与验证范围见[结果解释与限制](agentenv-results.md)和[任务索引](../results/agentenv/README.md)。

建议优先验证 **C4、CompCert、PDF.js**；HF 作为条件候选，Log4j 备用；Cython 或文本编辑保留为小工作集对照。是否最终入选，需要看分支是否复用共同历史文件、已有基线共享了多少，以及共享能否转化为实际内存和运行收益。

## 现有结果能支持到哪一步

目前已补齐逐工具时延、guest 内存与 page cache 曲线，以及每次工具结束后的文件驻留扫描，可支持任务类型和文件工作集的初筛。**当前最需要补齐的是低扰动对照，并据此修正采集方案。** 全根扫描会加载元数据，排除扫描期间的样本也不能消除后续影响；尚无相同镜像、相同轨迹但不做全根扫描的对照，不能简单扣除某个内存差值后当作纯业务需求。

学长提出的单任务 profiling 要求本身并不等于要求完成多 VM 物理共享实验。但若论文要声称“checkpoint 历史层 / 增量 DAX 减少重复占用”，则还需要新增验证：

- **共同历史文件是否被复用。** 识别基础镜像文件、分支前新增且封存的文件、分支私有输出，确认后缀实际读取哪些共同历史文件。单 VM 驻留和路径存在都不能单独证明这一点。
- **基线已经共享了多少。** 快照或只读映射可能已有物理共享；不能把各 guest 的文件驻留相加，就当作新增 DAX 能节省的内存。
- **host 实际占用是否降低。** 测量多个 VM 对应的唯一物理页与共享关系，并核对总占用；同内容文件、guest PFN 相同或各 VM 页数相近，都不等于同一 host 物理页。
- **收益是否覆盖成本。** 同时记录封层、checkpoint / restore、工具运行成本，明确缓存冷暖、回收策略和重复运行波动。

## 建议的下一步顺序（尚未执行）

1. **先修正测量。** 用 Matplotlib、Django 做相同镜像与轨迹的轻量计数对照，与当前全根扫描方案比较；如需区分额外等待和目录遍历的影响，增加等时长等待对照。根据结果确定主曲线采集方式，再决定哪些任务需要重采。
2. **先用 C4、CompCert 做共享试验。** 选择共同准备或构建完成的边界，核实哪些新文件会进入 checkpoint 历史层，再设计固定后缀。现有线性重放没有验证分支行为；相同后缀的多副本只用于机制校准，真实分支的复用仍需单独验证。
3. **从 1 / 2 / 4 个 VM 起步。** 在相同资源、输入、挂载与冷暖条件下比较基线和目标方案，测量文件页总量、host 唯一物理占用、共享量与运行成本；重复运行后报告波动，核对与 DAX 映射的统计范围，避免重复记账。
4. **再补 PDF.js 与一个小工作集对照。** HF 在确认实际模型文件访问和匿名内存构成后再决定是否入选。无需立即把十个任务全部扩展为共享实验。

**C4、CompCert 的 `/tmp` 必须先核实挂载和封层语义。** 两条轨迹都有大量文件位于 `/tmp`；若实际平台将它放在单独 tmpfs，或只归档恢复而不纳入 DAX 历史层，这批文件就不能直接用来证明历史层 DAX 的收益。应先确认目标文件所在的可封存文件系统；如需调整路径，所有比较方案使用一致的变更，并说明与原轨迹的差异。

共享验证应同时覆盖基础只读文件和 checkpoint 后产生的共同历史文件，以区分已有基础共享与增量收益。最终保留哪些任务，应由复用行为、实际物理占用和验证完整性共同决定；当前缓存峰值只提供候选线索。
